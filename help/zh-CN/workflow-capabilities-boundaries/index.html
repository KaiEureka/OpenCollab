Workflow 与子 Workflow

判断 Workflow 能实现的范围与运行边界

协作想法可以先拆成三个问题。控制顺序怎样表达，模型和工具怎样执行，运行外的业务状态由谁管理。普通 Python 能表达分支、循环、函数组合和动态依赖，OpenCollab 的 ctx 管理会话、容量、额度与候选环境，应用服务负责自己的数据库、外部系统和跨主机协调。按这三个来源安排方案，可以很快找到可执行的开发位置。

任意想法怎样变成程序

只要能用当前解释器、依赖和权限实现，Workflow 函数就能导入模块、调用业务函数、处理数据，再按输入或中间结果创建后续步骤。一个探索流程可以先观察资料，再判断缺少哪些信息，动态生成任务列表，最后汇总结果。分支用 if，有限迭代用 for，反馈循环用 while，这些语法由 Python 提供。

想法需要转成可观察的输入、行动和停止条件。工作流代码决定模型结果怎样影响下一步，模型的报告随后还需由文件、工具回执和实际检查支持。较长阻塞操作应交给异步库、线程或应用拥有的独立进程，以便保留事件循环的并发与取消响应。

动态图与组合深度

Workflow 可以自行维护节点表、完成结果和依赖集合，选择就绪节点交给 parallel，再把结果送入下一批。通用图的节点语义、失败传播和停止条件由作者定义。Weave 已提供分组依赖规划，依赖环中的组会合入同一个会话，适合采用其现成分组协议的任务。

普通异步子函数可以按业务拆分并共享 ctx。候选子流程建立独立候选环境，继续共享父会话容量、集合容量与绝对期限。当前默认候选子上下文未注入另一层候选后端，子流程内部再次建立候选需要集成提供相应能力。这样区分函数嵌套与环境嵌套，能够准确安排组合方式。

代码与工具分别在哪里执行

执行方式 Python 编排位置 Agent 工具位置
宿主 SDK 加 shared 调用方进程 借用当前环境和目录
宿主 SDK 加 worktree 调用方进程 父环境中的独立 checkout
宿主 SDK 加 docker-group 调用方进程 本次策略运行的容器，各会话私有工作区
宿主 SDK 加 docker-session 调用方进程 每会话独立容器与工作区
manage_workflow 源文件 成员环境内的 Python 子进程 按继承或单次选择的策略执行

worktree 共享操作系统和 Git 对象存储，容器环境中的 worktree 仍位于该容器。Docker 策略需要可用 Docker daemon 和合适镜像，默认网络为 none，挂载和网络按 provider 配置。宿主 Python 直接使用 Path 或 subprocess 时，行为仍取决于宿主进程的位置，Agent 的 Docker 配置主要决定工具环境。

自定义 provider 工厂每次为运行和策略创建 EnvironmentPool，负责 acquire、release 与 adopt。工具权限、工作区检查与输出限制仍按原协议生效。全环境候选后端还可决定活服务和文件如何一起交付。

运行时源文件与业务服务

Team 成员可以用编辑工具生成 Python 文件，再通过 manage_workflow launch 在自己的环境启动。成员需要 bash 权限、安装了 OpenCollab 的 Python，以及其子会话要用的工具授权。启动立即返回 id，创建者随后查询、等待和停止，父成员结束时清理剩余子运行。它使运行时生成编排代码成为已有执行路径。

普通 SDK Workflow 的并发参数管理本次运行中的会话和集合任务。多主机队列、远端 worker 注册、全局状态和跨系统资源所有权需要应用组件连接。保存的 workflow.json、会话和轨迹可追溯执行，通用控制流继续执行所需的状态与副作用处理则由应用设计。Weave 的显式状态继续可作为现有、范围明确的实现参考。

验证一个方案是否成立

先选最小真实输入，把控制流执行出来，记录实际发生的 Agent 调用与工具操作。然后确认文件、服务或返回值是否符合需求。completed 表达入口完成和执行状态，任务是否正确还需要真实入口、测试或应用验证器。依据这条可观察路径，就能区分一个想法已经由 Python 实现、需要接入某个 ctx 方法，还是需要应用服务补足。
